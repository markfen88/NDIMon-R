# Authoring NDIMon-R plugins

A plugin is trusted code running inside `ndimon-api`, with explicitly installed
root scripts. Install only archives from publishers you trust. An authenticated
appliance administrator can install plugins. HTTPS authenticates the feed server and protects transport integrity. SHA256
checks archive bytes against that trusted feed; it is not a publisher signature.
HTTP requires the explicit device setting `allow_insecure_feeds:true` and loses
those transport protections. Feed, checksum, archive and redirect URLs all use
the same policy.

## Layout and ownership

```text
/opt/ndimon-r/plugins/<name>/       root-owned, directories/executables 0755
  plugin.json
  routes.js
  ui.html
  backup.js
  install.sh
  uninstall.sh
  priv/<command>
  priv/ALLOWED                     generated by the host
/var/lib/ndimon/plugins/            root:root, 0755, registry parent
/var/lib/ndimon/plugins/<name>/     ndimon:ndimon, 0700, runtime state
/var/lib/ndimon/plugins/downloads/  ndimon:ndimon, 0700, temporary downloads
/etc/ndimon-plugins.json            API-owned enabled/version state
```

The registry parent is root-owned, but its ancestor `/var/lib/ndimon` is writable
by ndimon. Root operations pin directory descriptors and verify the registry
parent ownership and mode during both bundle and runtime-state traversal; a
pathname alone is not an ownership guarantee. Installer imports use fresh
private directories under `/var/lib/ndimon/import/`, with copies and downloads
performed as ndimon. Local source archives must be readable by that user.

JSON writes use `readJson`/`writeJson`; the latter uses the privileged atomic
config writer for `/etc`. Each configuration file has one designated writer.
Declare your plugin's other configuration files in `config_files` and document
their writer. Never put infrastructure credentials in an archive or repository.

## Manifest

```json
{
  "name": "hello",
  "version": "1.0.0-1",
  "title": "Hello",
  "min_ndimon": "1.3.0",
  "icon": "bi-puzzle",
  "routes": "routes.js",
  "ui": "ui.html",
  "backup": "backup.js",
  "install": "install.sh",
  "uninstall": "uninstall.sh",
  "priv_commands": ["ping"],
  "services": [],
  "supplementary_groups": [],
  "readwrite_paths": [],
  "config_files": []
}
```

`name`, `version`, `title`, and `min_ndimon` are required. Names and privileged
commands match `^[a-z][a-z0-9-]{1,31}$`; the title is 1–40 characters. Versions
use Debian ordering, including epoch, revision, and `~`. `min_ndimon` declares
the required host version; installation is refused with HTTP 409 `host_too_old` when the installed firmware
is older than this minimum. Direct privileged installs enforce the same minimum
with Debian ordering and exit 2 `host_too_old` when it is unmet or the firmware
version is unavailable. Authors must test compatibility on that version.

A minimum version is a compatibility floor, not a guarantee for every host
configuration. Publish a runtime update as a new plugin archive with its matching
version and bundle lock. Unknown manifest keys are refused.

The defaults are shown above; arrays default to empty. Set `backup` to `null`
to opt out. Unknown fields are rejected. Entry filenames must be simple local
filenames. Services are `.service` units; config and writable paths are absolute
paths without whitespace or systemd directive interpolation. The API's current
schema is in `api/plugin-manifest.js`. Services must equal `<name>.service` or start with `<name>-`, `<name>@`,
`ndimon-<name>.` or `ndimon-<name>-`, with exceptions for `tesserad.service` for tessera and
`bluealsa.service` for bluetooth; host API and SSH units are forbidden. Writable paths must
equal `/run/<name>`, `/var/lib/<name>` or `/etc/<name>`, or be below those
directories. Only tessera may also use `/run/tessera*`, `/var/lib/tessera*`
and `/etc/tessera*` add-on paths. Broad system directories are forbidden. Groups
`root`, `sudo`, `wheel`, `adm`, `shadow`, `disk`, `docker`, `lxd`, `kmem`,
`systemd-journal` and `ndimon` are forbidden. Root validation also rejects
existing groups with GID below 1000 except `audio`, `video`, `render`,
`bluetooth`, `tessera` and `tessera-admin`. The last two groups are available
only to tessera. Installed drop-ins grant these
groups and paths to the whole API process, including while a plugin is disabled.

## Router and status

```js
'use strict';
module.exports = host => {
  const router = require('express').Router();
  router.get('/ping', (req, res) => res.json({ pong: true }));
  router.status = () => ({ healthy: true });
  return router;
};
```

The router is mounted at `/v1/plugins/<name>` while enabled, behind normal auth
and Origin checks. The host supplies `sendIPC`, `readJson`, `writeJson`,
`runPriv`, `runPrivAsync`, `ipcEvents`, `pluginDir`, `stateDir`, `log`, and `audio`.
`audio` is the Track B `api/audio-settings.js` module when present, otherwise
`undefined`. Existing host npm dependencies are available to plugin entry modules;
no new dependency is required by the framework. Do not start listeners or block
the API loop. `router.status()` must return promptly with a JSON object;
exceptions are isolated and reported in the plugin status. `/api/status` and
status SSE include `plugins: [{name,state,version,title,icon,status}]`.

A loader exception marks the plugin `error` without stopping the API. Enable
state survives restart. Immediately after root installation, the API reads and
validates the installed manifest without executing plugin code. An install with
`enable:true` atomically saves `{installed:true, enabled:false,
pending_enable:true, version}` before attempting a router reload. That reload
provides feedback only: installation returns HTTP 200 with `state:'installed'`,
`restart_pending:true`, and `load_error` (a message or `null`), even if the old
API process cannot load the router. The persisted intent survives that error
and routes stay disabled until the next API start. Startup consumes the request before running enable hooks or
starting services, then saves enabled state on success. A failed attempt is
isolated as a plugin error, recorded in state as `enable_error`, and is not
replayed on another start. A startup router-load failure also consumes the
request and records the error; successful enable clears the prior error. Removed,
broken, or version-mismatched plugins are not enabled. `registry.ready` resolves
when startup processing finishes; the server waits for it before listening.
Ordinary registry reloads do not consume pending requests.
Disabled plugins load only backup hooks; their router factories do not run.
Enabled routers are reused across reloads until their version changes, when
cached plugin modules are invalidated. Broken plugins load no code. Corrupt
plugin state is treated as empty and logged; status includes
`plugins_state_error`, and the API continues listening. State writes and lifecycle
mutations return HTTP 409 `plugins_state_corrupt` until an administrator confirms
**Reset plugin state** in the warning banner. The authenticated
`POST /v1/plugins/state/reset` atomically recreates an empty state file and clears
the corruption latch. Installed code and plugin settings are kept, with all
plugins disabled; re-enable the desired plugins afterward. A failed reset keeps
the original file and blocks writes. Merely reloading the registry does not
clear the latch.

## UI fragment

Only the configured UI file is served, at `/plugins/<name>/ui.html`, under auth
and only while enabled. Keep content inside the pane supplied to your initializer.
Use the host's Bootstrap and helpers. Inline scripts are executed after insertion.
Use bracket notation for names containing hyphens:

```html
<div class="result"></div>
<script>
window['NDIMON_PLUGIN_INIT_hello'] = async function(pane) {
  const result = await window.NDIMON.get('/v1/plugins/hello/ping');
  pane.querySelector('.result').textContent = result.pong ? 'pong' : 'failed';
  const unsubscribe = window.NDIMON.onStatus(status => {
    // status.plugins holds the current plugin telemetry.
  });
  return unsubscribe;
};
</script>
```

`window.NDIMON = {get(url), post(url,body), toast(msg,type), onStatus(cb), state}`.
`state` is a getter for current host state, and `onStatus` returns an unsubscribe
function. The optional initializer receives its pane and may return a cleanup
function. Do not open another EventSource. Progress arrives on the existing
`/api/events` stream as `{type:'plugin_progress',name,step,error?}`. The separate
`api/plugin-events.js` helper observes that endpoint; `Status.js` only adds the
plugin summary field.

## Backup hooks

```js
'use strict';
module.exports = {
  export: () => ({ message: 'hello' }),
  validate: data => typeof data.message === 'string' ? null : 'message required',
  import: data => { /* write validated settings atomically */ },
};
```

Hooks are synchronous. Export includes enabled plugins with hooks in
`sections.plugins[name] = {version,data}`. Restore can import into an installed,
disabled plugin too. `Registry.backupHooks()` returns healthy installed/enabled
hooks; callers exporting must filter for enabled state. A missing plugin is
skipped with a warning; a validation or import failure affects that plugin only,
with details in `results.plugins`. The core settings restore still completes.
Plugin settings participate in the pre-restore snapshot and undo. Plugins are
not installed automatically by restore. Backup data must be a plain JSON object. Each export is serialized and parsed
inside its plugin's error boundary and capped at 1 MiB of UTF-8 JSON. Invalid,
cyclic, or oversized exports are skipped with a warning in the document's
`warnings` array, including during pre-restore snapshots. Empty `sections.plugins`
and `warnings` fields are omitted for compatibility with older devices.

## Root script contract

Archives contain `plugin.json` at the archive root (no enclosing name directory).
For example, create an archive on your packaging machine with
`tar -czf hello-plugin_1.0.0-1_amd64.tar.gz -C hello .`.
Only regular files and directories are accepted; no links, devices, traversal,
control characters, or duplicate archive entries. The root snapshot copy is
limited to 200 MiB. Members are inspected incrementally; the expanded archive is limited to 1 GiB and
20,000 members. A plugin can embed its own prebuilt add-on bundle.

The fixed privileged interfaces are:

- `ndimon-priv plugin-inspect <name> <archive.tar.gz> [--expect-version <version>]`
- `ndimon-priv plugin-install <name> <archive.tar.gz> [--expect-version <version>] [--force]`
- `ndimon-priv plugin-uninstall <name> [purge|force]`
- `ndimon-priv plugin-exec <name> <command> [args...]`
- `ndimon-priv service-ctl <start|stop|restart> <unit>`
- `ndimon-priv plugin-job-status <ndimon-plugin-name-pid.service>`
- `ndimon-priv plugin-job-cancel <ndimon-plugin-name-pid.service>`
- `ndimon-priv restart-api`

Install performs these steps:

1. Validate the name and resolve the archive inside
   `/var/lib/ndimon/plugins/downloads/` or `/var/lib/ndimon/import/`.
2. Run in a transient system-manager unit outside the API's `ProtectSystem=strict`
   mount namespace, named `ndimon-plugin-<name>-<pid>.service` with
   `RuntimeMaxSec=600`. Serialize root install/remove operations with a file lock.
3. Open each directory component and the ndimon-owned regular archive without
   following symlinks, copy from the pinned descriptor to root-controlled
   storage, validate members and manifest,
   check the name and expected version, refuse unforced downgrades, and extract
   to `.staging-<name>`.
4. Generate `priv/ALLOWED` from `priv_commands`; retain the old version as
   `.previous-<name>`, write `.broken` before running any install script, and
   move the new directory into place. Remove the marker only on success.
5. Prepare the private runtime state directory.
6. Run the manifest's install script with `/bin/bash`, from the plugin directory,
   with `NDIMON_PLUGIN_DIR` and `NDIMON_PLUGIN_STATE`. The script must install
   prebuilt binaries idempotently and exit nonzero on failure. Re-resolve every
   supplementary group after the script succeeds; missing or unsafe groups fail
   the install. Only then write `ndimon-api.service.d/plugin-<name>.conf` with
   supplementary groups and writable paths and reload systemd.
7. The API deletes the download, returns its result, and requests a deferred API
   restart so the new groups and paths take effect. The installer restarts the
   API after all requested plugins finish.

Install/uninstall scripts run as root. Make them idempotent, record what they
create, and never remove unrelated files. Uninstall receives the literal `purge`
argument when requested. Normal removal keeps plugin configuration/state;
`purge` removes the framework's state directory and lets the script purge its
own configuration. On failure, files are kept with a `.broken` marker and exit
4; a failed update restores the previous code and unit drop-in and marks it
broken for review. External package/config side effects require the plugin's
own recovery logic. Force removal skips the uninstall script, so it cannot
clean up that script's packages or services.

Exit codes: 0 success, 2 invalid input, 3 not allowed, 4 script failure.
Every plugin operation first restores `.previous-<name>` if the live directory
is missing. Service control ignores hidden and broken plugin directories.
`plugin-exec` holds the operation lock through execution and runs only exact commands in generated `priv/ALLOWED`, without
shell argument interpolation. An enable/disable command, when declared, owns
that transition; otherwise the framework starts/stops manifest services.

## Feeds and API

`plugin_feeds` in device settings is an array of Forgejo releases API URLs
(for example `https://forge.example/api/v1/repos/team/plugins/releases?limit=5`),
or directory `index.json` URLs. The directory document is
`{"plugins":[{"name":"hello","version":"1.0-1","arch":"amd64","asset_url":"https://forge.example/hello.tar.gz","sha256":"<64 hex digits>","size":123}]}`.
For Forgejo, assets are `<name>-plugin_<version>_<arm64|amd64>.tar.gz` plus
`SHA256SUMS` with exact asset names. The tessera add-on's `tessera-bundle_...`
archive belongs inside its plugin archive and is not a plugin feed asset.

Feeds time out within 10 seconds. They are refreshed on demand and at most every
15 minutes by the background cache timer, outside the status loop. Downloads
are streamed with SHA256 verification, a 200 MiB size cap, and a five-minute
timeout. An empty feed list gives an upload-only UI.

The authenticated lifecycle API is `GET /v1/plugins`, `GET /v1/plugins/feed`,
`POST /v1/plugins/feed/refresh`, `POST /v1/plugins/install` with
`{name,source:'feed'|'upload',version?,enable?,force?}`, and
`POST /v1/plugins/<name>/{enable,disable,update,uninstall}`. Uninstall accepts
`{purge,force}`; update requires a strictly newer feed version. Install binds
the archive version to the feed entry and refuses a downgrade unless `force:true`. Upload first uses
`POST /v1/plugins/upload?name=<name>` with `application/octet-stream` bytes,
then install with `source:'upload'`. Fresh API installs are disabled unless
`enable:true` is specified; that queues enabling for the next API start, and the
UI requests it explicitly. Every successful root install schedules the API
restart after its HTTP response, including when later state handling fails. Successful uninstall
atomically removes the saved enabled/version entry. A second mutation returns 409 `busy` while
one operation is in progress. On a five-minute wait timeout the API cancels the
named root job and confirms it is inactive before allowing another mutation.
If cancellation/status cannot establish termination, mutations stay blocked;
subsequent requests recheck the job. A timeout without a job marker requires
operator investigation. The GET list includes registry entries, cached
feed metadata, and normalized architecture (`amd64` or `arm64`).
