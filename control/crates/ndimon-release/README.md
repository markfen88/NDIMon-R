# ndimon-release

Release verification for signed updates. The privd update agent uses it before
installing a package, `ndimon-state` uses it to tell whether a device has any
trusted key, and `cargo xtask release`, `verify-release` and `release-smoke` use it
to sign and check release directories.

## Verification

`verify_manifest(manifest, signature, keys, version)` verifies the minisign
signature (prehashed `ED` only; the legacy `Ed` form is refused, as Tessera also
requires) and its trusted comment before it parses a single checksum. The trusted
comment is exactly `product:ndimon-r<TAB>version:VERSION<TAB>file:SHA256SUMS`, and
the signature binds both the manifest bytes and that comment. An empty key list
fails closed with `untrusted_key`, even for malformed input.

`Manifest` accepts GNU coreutils text or binary SHA-256 records with LF endings,
64 hexadecimal digits and unique flat release filenames (`valid_filename`). Paths,
escaped names, control characters, blank lines and the manifest's own names
(`SHA256SUMS`, `SHA256SUMS.minisig`) are refused. `verify_reader` streams SHA-256,
and `verify_file` refuses a symlink or any nonregular asset. Callers keep verified
files in their private staging directory until use.

Errors have stable `code()` values: `untrusted_key`, `bad_signature`,
`wrong_product`, `wrong_version`, `missing_file`, `checksum_mismatch`, `malformed`.

## Trusted keys

`TRUSTED_KEYS` is intentionally empty: the project's first public key is provisioned
by the owner and no key is generated by the build. Device callers combine it with
`trust::load_keys("/etc/ndimon/trusted-release-keys")`. That optional file holds one
bare minisign public key per line, must be a root-owned 0644 regular file, and all
its ancestors must be root-owned and not group- or world-writable; symlinks are
refused (`trust::read_config`). With no keys configured every verification returns
`untrusted_key` and the device is updated by installing a verified package set by
hand. An override file adds keys; it never revokes a compiled key. A rotation ships
the new key in a release signed with a key that is already trusted. The operator
procedure is in [Signed releases and updates](../../../docs/releases.md).
